# validate-browser-finding

Browser-based security validation using an **onion-layer methodology**: prove the exploit at the innermost layer (bare app, simple auth), then progressively add real-world defenses to confirm each layer's contribution to blocking the attack.

## Onion Layers

```
Layer 4: Full stack (IdP + TLS + ingress + app)        ← production reality
Layer 3: App + middleware (oauth-proxy, CSRF tokens)   ← defense layer
Layer 2: App + simple auth (form login, session)       ← authenticated surface
Layer 1: Bare app (no auth or trivial auth)            ← last line of defense
```

**Start at Layer 1.** If the exploit confirms, move outward. Each layer either blocks the attack (refuted → that layer is the defense) or passes it through (confirmed → escalate).

This answers: "Is the app *inherently* vulnerable, or does it rely on external middleware for protection?"

## How It Differs from validate-findings

| | validate-findings | validate-browser-finding |
|---|---|---|
| Domain | K8s operators, containers, WASM | Web apps, APIs via browser |
| Plan source | Auto-generated by plan.py from audit JSON | Hand-crafted attack-plan.yaml |
| Adapter | k8s, container, wasm | browser (+ container for setup) |
| Lab | OCP cluster / docker containers | docker-compose (app + attacker + playwright) |
| Evidence | Logs, manifests, WASM output | HAR, screenshots, DOM state, cookies |

Browser targets may specify an `expires` date (valid through that date) or a
timezone-aware ISO datetime (valid until that instant). Naive or malformed
timestamps are refused, and each browser action rechecks the current deadline.
Reports keep `metadata.expires` date-only and preserve a precise deadline in
`metadata.additional.validation_producer.expires_at`.

## Usage

### Layer 1-2: Local (all severities)

```bash
# 1. Start the lab
cd analysis-results/validations/hawtio-csrf
podman compose up -d

# 2. Run validation
cd ../../traust/harnessing/5-validate/validate-browser-finding
python run.py ../../../analysis-results/validations/hawtio-csrf/

# 3. Check results
cat ../../../analysis-results/validations/hawtio-csrf/hawtio-csrf-validation.json
```

### Layer 3-4: OCP cluster (high/critical only)

If Layer 1-2 confirms, escalate to real infrastructure:

```bash
# 1. Provision cluster (security-testing-clusters)
cd security-testing-clusters && terraform apply

# 2. Deploy target with oauth-proxy sidecar + Route
oc new-project hawtio-csrf-lab
oc apply -f validations/hawtio-csrf/ocp/deployment.yaml

# 3. Run same validation against cluster Route
python run.py validations/hawtio-csrf/ \
  --targets validations/hawtio-csrf/targets-ocp.yaml

# 4. Teardown
terraform destroy
```

## Validation Directory Structure

```
validations/<name>/
├── *-attack-plan.yaml   # Ordered steps (adapter, verb, target, expected)
├── *-security-audit.json # Source finding (optional, for report linkage)
├── targets.yaml          # Scope: browser origins, credentials, allowed verbs
├── docker-compose.yaml   # Lab definition
├── exploit-page/         # HTML PoCs served by attacker container
└── artifacts/            # Generated: screenshots, HARs, logs
```

## Attack Plan Format

```yaml
metadata:
  finding: "FINDING-ID"
  date: "2026-07-09"
  engagement: "internal-lab"

steps:
  - id: step-001
    adapter: browser
    verb: authenticate
    target:
      url: "http://victim:8080"
    classification: safe
    expected: "Session established"

  - id: step-002
    adapter: browser
    verb: csrf-replay
    target:
      url: "http://attacker:8000/exploit.html"
    payload:
      attack_origin: "http://attacker:8000"
    classification: mutating
    expected: "Cookie sent cross-site on GET form"
    preconditions: [step-001]

chains:
  - chain_id: csrf-chain-1
    name: "CSRF via GET form submission"
    entry_point: "attacker page"
    terminal_asset: "JMX execution"
```

## Supported Verbs

| Verb | Classification | What It Does |
|------|--------|------|
| navigate | safe | Load URL, capture response |
| screenshot | safe | Page screenshot to artifacts |
| har-capture | safe | Record network traffic |
| inspect-cookies | safe | Dump cookie jar |
| check-headers | safe | Capture response headers |
| check-csp | safe | Parse Content-Security-Policy |
| dom-query | safe | Query DOM elements |
| authenticate | mutating | Login via form fill |
| csrf-replay | mutating | Cross-origin form/navigation attack |
| form-submit | mutating | Submit form within origin |
| xhr-probe | mutating | Fire XHR/fetch cross-origin |
| xss-inject | mutating | Test reflected/stored XSS |
| clickjack-probe | mutating | Frame target in attacker page |
| redirect-probe | mutating | Open redirect tests |

## Layer Progression (per validation)

Each validation directory can have multiple docker-compose variants:

```
validations/hawtio-csrf/
├── docker-compose.yaml           # Layer 1: bare app + attacker + browser
├── docker-compose.layer2.yaml    # Layer 2: app with auth enabled
├── docker-compose.layer3.yaml    # Layer 3: + oauth-proxy or CSRF middleware
└── docker-compose.layer4.yaml    # Layer 4: + Keycloak/Dex + TLS
```

Run each layer separately. The report captures which layer blocked the attack:
- Confirmed at L1, refuted at L3 → app is vulnerable, middleware compensates
- Confirmed through L4 → exploitable in production (critical)
- Refuted at L1 → app handles it natively

## Current Status

**Implemented (Layer 1–2):**
- Form-fill authentication
- Cross-origin CSRF replay (GET form, POST form)
- Cookie/header inspection
- HAR capture, screenshots
- Scope enforcement (origin allowlist, verb restrictions)

**Not yet implemented (Layer 3–4):**
- OAuth/OIDC redirect flow completion
- Double-submit CSRF token extraction + header injection
- oauth-proxy session cookie handling
- TLS certificate trust for self-signed lab certs
- Ingress/route-level header injection testing
